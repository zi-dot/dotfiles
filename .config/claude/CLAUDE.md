# 開発ガイドライン

## 基本開発原則
- **SOLID原則**: SOLID原則を重視し、特に命名と設計においてOpen-Closed Principle (OCP)を適用
- **DRY, KISS, YAGNI**: コードをクリーンでシンプルに保ち、過度な設計を避ける
- **GoF Design Patterns**: 適切な場合にDesign Patternsを適用

## コード調査
- 既存のコードベースを調査する場合、初期調査は必ず ask_devin mcp を利用する。
- 既存のコードベースに関して、Searchは基本的に使わず ask_devin mcp を優先的に利用する。
  - その際には、repo名として `knowledge-work/knowledgework` を指定する。
  - ただし、ask_devin mcp はmasterブランチのコードを参照するため、ローカルのコードを参照したい場合はSearchを利用する。

## 命名規則

### 変数と関数
- 全ての変数と関数名には**camelCase**を使用
- ループには一時変数 `i`, `j`, `k` を使用
- Boolean変数は自然な英語として読める形にする（例：`isVisible`, `hasData`, `canSubmit`）
- 汎用的なものではなく、具体的で説明的な動詞を関数に使用
  - ✅ `calculateTotalPrice()`, `validateUserInput()`
  - ❌ `processData()`, `handleStuff()`

### 定数と設定
- 定数には**UPPER_SNAKE_CASE**を使用（例：`MAX_RETRY_COUNT`）
- マジックナンバーと設定値をReactコンポーネント外に抽出
- コンポーネントロジックとは別に設定を定義

### 非同期関数
- 非同期関数に特別な命名規則はなし
- 実行される具体的なアクションに基づいて命名

## コマンド実行
- cd は基本的に利用しない
- pnpm スクリプトを実行するときは -F オプションを使用して特定のパッケージを指定
  - 例: `pnpm -F product-process test`
- typecheck, lint, formatなどのコマンドを使う場合は --affected オプションを使用して影響を受けるパッケージのみを対象にする。ただし、-F オプションの場合は利用しなくて良い。
  - 例: `pnpm typecheck --affected`

## エラー処理

### 例外処理
- try-catchブロックのサイズは過度に細分化せず、ビジネス要件に応じて調整
- デフォルトでは標準の`Error`オブジェクトを使用
- プロジェクトで既に確立されたパターンがある場合のみカスタムエラークラスを使用

### 非同期エラー処理
- 非同期関数では例外をキャッチするのではなく**エラーをthrow**
- 適切なエラー処理のためにReactの**Error Boundaries**を活用
- ユーザー向けエラーメッセージと内部ログを分離

### エラーログ
- ユーザー表示エラーと内部ログの分離を維持
- デバッグに十分な詳細をログに記録し、ユーザーメッセージは明確に保つ

## テスト戦略

### テストタイプとカバレッジ目標
- **Unit Tests**: 関数にVitestを使用して約100%カバレッジ
- **Component Tests**: integration testとして**Storybook Play**関数を使用（約80%カバレッジ）
- **E2E Tests**: 低いカバレッジで、重要なユーザージャーニーに焦点

### テストアプローチ
- **AAAパターン**（Arrange-Act-Assert）に従う
- リソース/ドメイン別に整理されたモック関数を作成
- **正常ケースとエッジケース**に焦点、エラーシナリオを含む
- カスタムhookのテストは独立したテストではなく主にPlayテストを通じて実施

### テスト哲学
- コンポーネントテストには主に`getByRole`を使用
- 実装詳細ではなく**ユーザー視点**でテストを記述
- コンポーネントテストは以下をカバー：正常フロー、エッジケース、エラー状態

## コード構成

### ディレクトリ構造
- 利用可能な場合はプロジェクト規則に従う
- レイヤーベースよりも**ドメイン/機能ベース**の構成を優先
- 関連機能をグループ化

### ファイル構成
- 可能な限りファイルを500行以下に保つ
- 型定義とヘルパーはそれぞれのドメイン内に配置
- コンポーネント固有のユーティリティ：同じファイルまたは隣接ファイル
- **線形依存チェーン**を維持し、循環参照を避ける
- 循環依存を防ぐためにlintingルールを使用

### 状態管理
- デフォルトで**ローカル状態**を優先
- 必要な場合のみグローバル状態を使用
- グローバル状態管理には**Zustand**または**Jotai**を選択
- プロジェクトで既に使用されていない限りReduxを避ける

### コンポーネントアーキテクチャ
- **Container/Presentational**分離を適用
- UI要素（例：製品カード）にはpresentational componentを強く重視
- 同じ機能で3つ以上の関連変数を管理する場合はカスタムhookを抽出

## ドキュメントスタイル

### コメントとドキュメント
- 特に必要でない限り**JSDocを避ける**
- 以下の場合にインラインコメントを記述：
  - ビジネス要件と仕様
  - 代替案よりも1つのアプローチを選択した理由
  - コードだけでは明らかでないコンテキスト
- **明らかなコードにはコメントしない** - コードを自己文書化させる

### TypeScript使用法
- **厳密で正確な型**を記述
- 外部モジュールで必要な場合のみ型をexport
- デフォルトで型を内部に保持し、必要時にexport

### Pull Requestドキュメント
PR説明を以下の順序で構成：
1. **機能説明**: これは何を達成するか？
2. **実装アプローチ**: どのように構築されたか？
3. **実装詳細**: 行われた具体的な変更

レビュアーがdiffを見る前に実装を理解できるように説明を記述。

### 複雑なビジネスロジック
複雑な関数については以下を文書化：
- **目的**: この関数は何を達成するか？
- **入力/出力**: 期待されるパラメータと戻り値
- **プロセス**: 複雑なロジックの段階的説明
- 明らかでないビジネスルールを説明するためにインラインコメントを使用

## Storybookガイドライン
- storyのプロジェクト命名規則に従う
- 現在Docsページは使用していない（将来追加される可能性あり）
- 主要な統合テスト手法としてPlay関数を使用

## プロジェクトメモリとコンテキスト管理

### プロジェクト固有のドキュメント
- ユーザーとやり取りする際は、以下のような重要なプロジェクト情報を記録：
  - コーディング規則とスタイル設定
  - アーキテクチャ決定とパターン
  - プロジェクト概要とビジネスコンテキスト
  - テクノロジースタックとフレームワーク選択
  - 開発ワークフローとツール設定
- 将来の参照のために`~/.claude/{project-name}.md`にこの情報を保存
- 存在しない場合はプロジェクト固有のファイルを作成
- 開発セッション全体での一貫性を確保し、プロジェクトコンテキストを維持

### TDD実践のコツ（t-wada流）

1. **最初のテスト**: まず失敗するテストを書く（コンパイルエラーもOK）
2. **仮実装**: テストを通すためにベタ書きでもOK（例：`return 42`）
3. **三角測量**: 2つ目、3つ目のテストケースで一般化する
4. **リファクタリング**: テストが通った後で整理する
5. **TODOリスト更新**: 実装中に思いついたことはすぐリストに追加
6. **1つずつ**: 複数のテストを同時に書かない

## Codexレビュー

### コードレビュー
- コードを実装した後は、Codex MCP (`mcp__codex__codex`) を使用してコードレビューを実施すること
- レビュー観点: コード品質、バグ、セキュリティ、パフォーマンス
- `sandbox: "read-only"` を使用

### 設計レビュー
- plan mode完了後や設計を伴う実装後は、Codex MCP を使用して設計レビューを実施すること
- レビュー観点: SOLID原則、設計パターン、責務分離、拡張性
- `include-plan-tool: true` を使用

# 重要な指示
- 求められたことを実行し、それ以上でも以下でもない
- 目標達成に絶対必要でない限りファイルを作成しない
- 新しいファイルを作成するよりも既存ファイルの編集を常に優先
- ユーザーから明示的に要求されない限り、proactiveにドキュメントファイル（*.md）やREADMEファイルを作成しない
- コードに変更を加えた場合は、確認を取らずに自動的にcommit & pushを行う
